# sequentialist-monitor

Мониторинг оборудования, процессов и энергии (`sequentialist.monitor`).
Версия 0.1.0 написана по ТЗ (документ «sequentialist-monitor 0.1 —
техническое задание», раздел 11 — этапы), не опубликована; README —
описание, гарантии, проверки и ограничения.

## Семейство

Библиотеки sequentialist — прикладной слой над ядром
[sequential-analysis](https://github.com/andre-a-no/sequential-analysis)

## Постоянные правила

- **Статистика — только в ядре.** Ядро и sequentialist-core из этого
  репозитория не править. Чего не хватает — список запросов: что нужно,
  зачем, какой интерфейс. Запрос к core — то, что нужно хотя бы половине
  прикладных пакетов; что уже в core, обратно не выносится.
- **Гарантии.** Каждый вывод называет свою гарантию (`exact`, `asymptotic`,
  `model`, `approximate`, `none`) так, как её объявляет процедура ядра.
  Утверждения честные и сдержанные; ничего не обещать без проверки тестом.
- **Сверка с эталонами.** Каждая процедура и каждый результат сверяются с
  внешней эталонной реализацией или закрытой формулой, где она есть.
- **Python ≥3.8**, обязательных зависимостей, кроме ядра и core, нет.
  Перед пушем: `ruff check .`, `mypy`, тесты, `vermin -t=3.8-`; CI должен
  быть зелёным.
- **Лицензии:** AGPL-3.0-only или коммерческая (COMMERCIAL.md); в каждом
  исходном файле SPDX-заголовок без города.
- **Чужой код принимается только по CLA** (`CLA.md`): без него код
  участника нельзя предлагать по коммерческой лицензии. PR без
  подписанного CLA не сливать. В CLA нет оговорки о подсудности и нет
  города — так решил владелец.
- **Этот файл (`CLAUDE.md`) оставлен по решению владельца.** Правило
  «никаких инструкций для мейнтейнеров в репозитории» — про заметки для

- **Контакты** в публичных файлах — только email: a.hobukob@gmail.com,
  andrei@hobukob.ru. Никаких телефонов, адрес компании не указывать.
- **Никаких идентификаторов моделей** в коммитах, PR и коде.

## Задача заказчика (реальный завод)

- Классы задач: дрейф и сдвиги процесса; состояние оборудования; энергия.
- Источники: историан / SQL, CSV, MQTT, OPC UA.
- Масштаб: сотни–тысячи сигналов, период — секунды.
- Куда тревоги: оператор в SCADA/HMI, мессенджер или почта, система ТОиР.
- Ещё не известно: ОС промышленных ПК (Windows или Linux), тип SCADA и
  удобный ей канал (OPC UA, Modbus, своё), будет ли выгрузка реальной
  истории с известными событиями (отказ, дрейф, перерасход) — на ней
  проверять ARL и время обнаружения до выхода на завод.

## Решения по 0.1 (согласованы с владельцем)

1. **Задача = агрегат** (например, насос Н-101 с 10–50 тегами); каждый тег
   и детектор — поток. Журнал пишется пакетом на агрегат за цикл опроса.
   Агрегаты — отдельные задачи, шардируются.
2. **Конвейер на тег: окно → модель → остаток → детектор.** Гарантии
   детекторов (ARL до ложной тревоги) опираются на независимость или
   мартингальную структуру; на сырых автокоррелированных данных они не
   выполняются. Окна (среднее, размах, максимум), прогноз на шаг (AR или
   Калман из ядра), детектор на остатках. Гарантия конвейера — `model`, и в
   отчётах она так и подписана.
3. **Бюджет ложных тревог задаётся для завода** (ориентир ISA-18.2: не
   больше ~6 тревог в час на оператора в норме) и раскладывается на ARL
   каждого детектора с учётом числа тегов и частоты. Для e-детекторов это
   точная граница при выполненных условиях, для остальных — оценка
   симуляцией (`sequentialist.core.simulate`).
4. **Базовая линия по эталонному периоду** истории; оценённые параметры
   далее считаются известными — в отчёте это оговаривается.
5. **Управление тревогами по ISA-18.2 / IEC 62682**: норма → активна не
   квитирована → квитирована → возврат; приоритеты, квитирование, шелвинг с
   истечением, вывод из работы — команды с исполнителем и причиной в аудите;
   подавление дребезга; KPI (тревог на оператора за 10 минут, долго висящие,
   дребезжащие, топ-10 источников).
6. **Не система ПАЗ**, только советующая; на IEC 61511 и SIL не
   претендуем — в README и в каждом отчёте.
7. **Модели данных открытых стандартов на границах, без зависимостей.**
   Тревога — подсостояния OPC UA Alarms & Conditions (`ActiveState`,
   `AckedState`, `ShelvingState` по времени и однократный,
   `SuppressedState`, `OutOfServiceState`), `Severity` 1–1000, событие в
   полях A&C (вебхук, HTTP API); качество значения — StatusCode OPC UA
   (Good / Uncertain / Bad); иерархия ISA-95 site → area → unit → тег, id
   латиницей (`[A-Za-z0-9_-]`, из них id задачи core), отображаемое имя —
   поле `name`; ISO 13374 (OSA-CBM) — словарь блоков в документации; время
   ISO 8601 UTC, единицы — коды UNECE. Писать «следует OPC UA A&C», не
   «соответствует»: соответствие — только сертификацией OPC Foundation.

|---|---|---|
| Дрейф и сдвиги | CUSUM, Shiryaev–Roberts, e-детекторы среднего и квантиля на остатках модели | — |
| Состояние оборудования | Калман: уровень и тренд; BOCPD для небольшого числа тегов | HMM, признаки по высокочастотным окнам |

**Протоколы (отложено, новых репозиториев пока не заводить).** Клиент и
сервер OPC UA (`asyncua`: LGPL-3.0+, Python ≥3.10), MQTT с Sparkplug B
(`paho-mqtt`: EPL-2.0 или BSD-3, берём BSD-3), Modbus TCP (`pymodbus`:
BSD-3, Python ≥3.10). Лицензии AGPL не мешают; разводить их по
репозиториям не нужно — лицензия привязана к поставке, extra не попадает в
наш wheel. Против extras в monitor — версия Python (≥3.10 против ≥3.8) и
транзитивные зависимости, поэтому, когда дойдёт до протоколов, вероятно,
отдельный пакет `sequentialist-connectors` (MQTT нужен и release/mlops);
решает владелец. Monitor задаёт протоколы источника и получателя тревог на
стандартной библиотеке, чтобы адаптеры подключались без его изменений.
Перед первой поставкой с `asyncua` (особенно офлайн-установщиком): в
COMMERCIAL.md — фраза о сторонних компонентах под своими лицензиями,
показать юристу; при раздаче `asyncua` — текст LGPL и исходники.

## Принято при реализации 0.1 (ждёт подтверждения владельца, ТЗ 11.4)

- Уровень и тренд — `ExponentialSmoothing` с подгонкой `fit_ets` (модели
  `level`, `trend`); Калман — с q и r вручную (`kalman_level`): подгонки
  Калмана в ядре нет (запрос 7).
- Порог CUSUM и BOCPD — симуляцией (`approximate`), наименьший, чья
  нижняя 95%-граница ARL достигает цели; SR и e-детекторы — порог = ARL
  (граница ядра).
- Задержка снятия `clear_after` — 30 окон (не 10): при устойчивом сдвиге
  остаток AR(1) ослаблен в (1 − φ) раз, CUSUM срабатывает снова через
  несколько окон, и короткая задержка заставляет тревогу «моргать» (тест).
  Сдвиг меньше расчётного всё равно может давать повторные активации —
  ограничение 0.1 (README), запрос 9 к ядру.
- Контрольные точки: сервис пишет их по очереди (каждый агрегат раз в
  `checkpoint_interval`, 300 с), движок — только после решений. Замер:
  2000 тегов × 1 Гц, цикл 5 с — 95% циклов 0.52 с (3.13) и 0.72 с (3.8);
  инкрементные контрольные точки core не нужны.
- `seq` плотные по каждому агрегату и источнику, курсор источника —
  записью в журнале агрегата (обход до запроса 1 к core).
- Окна выровнены по эпохе; окно закрывается водяным знаком (конец +
  `lateness`); неизвестное условие «в работе» в начале — не в работе.
- Проверка на SKAB (examples/skab.py): 33 из 33 неисправностей с
  тревогой (медиана 26 с), но ложных тревог 61/ч при расчётных 16/ч —
  модели на 400 с коротких нестационарных опытов не держатся; так и
  написано в README.

## Выпуск на PyPI (`.github/workflows/publish.yml`)

Как в sequentialist-core: запускается публикацией GitHub-релиза или вручную
с указанием тега; тег должен быть `v` + версия из `version.py`, иначе
публикация останавливается. Перед загрузкой — сборка, `twine check
--strict` и тесты на собранном wheel. Trusted publishing без токенов:
издатель на PyPI должен совпадать буква в букву — владелец `andre-a-no`,
репозиторий `sequentialist-monitor`, workflow `publish.yml`, environment
`pypi`.

Monitor выпускается только после core: workflow проверяет, что
`sequentialist-core>=0.1,<0.2` скачивается с PyPI, и ставит его оттуда для
тестов. Релиз `v0.1.0` в этом репозитории уже есть, но указывает на
`5540c48` (лицензии и план, без кода пакета); перед выпуском 0.1.0 его
нужно удалить вместе с тегом и выпустить заново после слияния кода.

## Запросы к ядру (не выполнены)

1. Самонастраивающиеся детекторы: CUSUM и e-детекторы с оцениваемой
   нормой и честной гарантией.
2. e-детектор на остатках прогноза с явной гарантией `model`.
3. EWMA-карта; CUSUM с поправкой на риск; MaxSPRT; двухвыборочный тест
   квантилей; ядерный e-детектор.
4. Быстрый BOCPD: при 2000 гипотезах шаг — порядка миллисекунд, это много
   для тысяч тегов.
5. Гарантия `Chain` (и `Lagged`) — самая слабая из гарантий стадий
   (exact > asymptotic > model > approximate > none). Сейчас они наследуют
   `none` от `Procedure`, и конвейер «модель → детектор» одним потоком
   подписан `none` вместо `model`. Интерфейс: атрибут `guarantee`
   экземпляра. Пока monitor держит модель и детектор отдельными потоками.
6. ARL для CUSUM. Объявить у `CUSUM` границу ARL ≥ e^h (CUSUM не больше
   логарифма статистики SR, Pollak) и дать подбор порога под заданный ARL
   для семейств (Brook–Evans или эквивалент) с объявленной гарантией.
   Зачем: раскладка бюджета ложных тревог на пороги без симуляции.
   Интерфейс, например: `cusum_threshold(family, theta0, theta1, arl)` →
   порог и гарантия; функция ARL для данного порога.
7. Подгонка `LocalLevelKalman` и `KalmanFilter` (q, r и др.) по истории
   максимумом правдоподобия → `ForecastFit`, как `fit_ar` и `fit_ets`.
   Зачем: решение «Калман: уровень и тренд»; до этого уровень и тренд в
   monitor считаются через `ExponentialSmoothing` и `fit_ets`.
8. Тест белого шума остатков (Ljung–Box) по истории: статистика, p-value,
   гарантия `asymptotic`. Зачем: проверка условий гарантии детекторов при
   калибровке; сейчас monitor показывает только описательные
   автокорреляции с гарантией `none`.
9. Проверка возврата в норму после тревоги: последовательная процедура,
   которая с объявленной гарантией подтверждает, что остаток снова имеет
   среднее 0 (например, e-процесс против сдвига величины, найденной при
   тревоге). Зачем: сейчас тревога снимается по «тишине» перезапущенного
   детектора `clear_after` окон, и устойчивый сдвиг меньше расчётного
   даёт повторные активации. Интерфейс: процедура на `{"z"}`, терминальная
   при подтверждении возврата, с ARL до ложного «возврата».

## Запросы к core (приняты владельцем, не выполнены)

Выпуск — sequentialist-core 0.1.1 (0.1.0 = коммит `27f7184`, его не
переписывать); после выпуска monitor закрепляет новый коммит.

1. Приём источников с пропусками в `seq`. Сейчас приём задачи
   (`Delivery("arrival", dedup=True)`) хранит каждый номер за пропуском,
   поэтому метка времени или id строки историана как `seq` раздувают
   контрольную точку, и monitor ведёт свой курсор в handler. Нужен режим
   «по возрастанию»: внутри source `seq` растёт, номер не больше последнего
   принятого — дубль; реализуется через `Delivery.skip_range` ядра, режим по
   умолчанию не меняется. Интерфейс, например:
   `Engine.create(..., intake="ordered")`, режим хранится в состоянии задачи.
2. Проверка команды до записи в журнал. Сейчас проверяется только имя;
   команда, которую handler отвергает по состоянию (квитирование
   квитированной тревоги), роняет задачу при каждом replay. Интерфейс,
   например: необязательный `Handler.check_command(command) -> str | None`
   (причина отказа); `Task.command` отказывает без записи в журнал.
3. Средняя длина серии с интервалом Монте-Карло в `simulate`, рядом с
   `Proportion`. Зачем: ARL детекторов в monitor, средний объём выборки в
   quality.

Живут в monitor до второго потребителя: `EmailSink` на `smtplib`.
Вопрос владельцу: доставка уведомлений «не менее одного раза» (сейчас
уведомление уходит после контрольной точки и теряется при падении между
ними). Инкрементные контрольные точки — только если не пройдёт замер на
2000 тегах × 1 Гц.
